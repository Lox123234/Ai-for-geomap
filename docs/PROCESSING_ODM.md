# Фотограмметрическая обработка: OpenDroneMap

GeoMap AI строит ортофотопланы, облака точек, модели рельефа и 3D-модели с помощью [OpenDroneMap](https://github.com/OpenDroneMap/ODM) (ODM). ODM — отдельная программа с собственной лицензией (AGPL-3.0). Она запускается в контейнере Docker отдельным процессом и не входит в поставку GeoMap AI.

**Docker и ODM нужны только для обработки.** Проекты, импорт, просмотр снимков и GPS-обзор работают без них. Если Docker нет или он не запущен, вкладка «Обработка» показывает причину и что сделать, а запуск обработки недоступен.

## Требования

| Что | Зачем |
| --- | --- |
| Docker Desktop (Windows, WSL 2) или Docker Engine (Linux) | запуск контейнера ODM |
| Образ `opendronemap/odm:3.6.2`, закреплённый по digest `sha256:94a0dd2714be4e8b565bdabd8f67e0191f36e37d82c179433adcb0a403aac3bd` | сам движок; около 630 МБ загрузки, около 2,4 ГБ на диске |
| Память, выделенная Docker | по справке ODM — около 1 ГБ на поток; при нехватке ODM завершается с кодом 137 |
| Свободное место на диске проекта | оценка по профилю (см. ниже) + 512 МиБ запаса |

Образ загружается только по кнопке «Загрузить образ ODM» после подтверждения в диалоге. GeoMap AI запускает именно образ с этим digest (`opendronemap/odm@sha256:…`), поэтому обновление тега `3.6.2` в Docker Hub не меняет движок незаметно.

Путь к клиенту Docker ищется в `PATH`, затем в стандартных папках Docker Desktop. Другой путь можно задать переменной окружения `GEOMAP_DOCKER` (полный путь к `docker`/`docker.exe`).

## Как проходит обработка

1. **Проверка окружения** (при первом открытии вкладки и по кнопке «Проверить снова»), асинхронно: `docker version` (служба отвечает), `docker image inspect` (образ загружен), `docker info` (CPU и память Docker).
2. **Предварительная проверка** при выборе профиля и параметров: файлы снимков на месте и не пустые, формат принимается ODM (JPEG, PNG, TIFF), снимков не меньше 2, наличие GPS, свободное место, допустимость дополнительных параметров, предупреждения о ресурсах. Ошибки блокируют запуск, предупреждения — нет.
3. **Создание задания** — папка `jobs/<id>/` в проекте, `id` — время создания (`20261014-073552`). Задание попадает в очередь; одновременно выполняется одно задание.
4. **Подготовка** (в фоновом потоке): каждый снимок проверяется чтением заголовка и помещается в `jobs/<id>/images/` жёсткой ссылкой на копию из `photos/` (без дополнительного места на диске; если файловая система не поддерживает жёсткие ссылки — копируется).
5. **Запуск** — `docker run` со списком аргументов, без командной оболочки:

   ```text
   docker run --rm --name geomap-odm-<id>
     -v <проект>\jobs\<id>:/datasets/code
     -v <проект>\jobs\<id>\images:/datasets/code/images:ro
     opendronemap/odm@sha256:94a0dd27… --project-path /datasets code <параметры профиля> --max-concurrency <N>
   ```

   На Linux вместо `-v` используется `--mount type=bind,source=…,target=…[,readonly]` с экранированием по правилам CSV, поэтому пробелы, запятые, кавычки и кириллица в пути проекта допустимы. Снимки монтируются только для чтения: ODM не может изменить файлы проекта, на которые указывают жёсткие ссылки.
6. **Ход работы** — строки вывода ODM пишутся в `jobs/<id>/log.txt`. Этап определяется по строкам `Running <этап> stage` и показывается как «Этап k из 13». Процентов нет: этапы ODM несопоставимы по длительности, и номер этапа не означает долю работы. Пропущенные в профиле этапы (например, `openmvs` в быстром режиме) не показываются.
7. **Завершение** — регистрируются найденные результаты с проверкой файлов (см. ниже). Код 0 без единого результата считается ошибкой. Код 137 сообщается как вероятная нехватка памяти Docker.

`--max-concurrency` выбирается автоматически: `min(CPU Docker, память Docker в ГБ − 1)`, но не меньше 1. Его можно задать вручную в дополнительных параметрах.

## Профили

Параметры задаются в `OdmEngine::profiles()`; при изменении обновите эту таблицу.

| Профиль | Параметры ODM | Результаты | Оценка места на диске |
| --- | --- | --- | --- |
| Быстрый просмотр | `--fast-orthophoto --feature-quality medium --orthophoto-resolution 10` | ортофотоплан по разреженной реконструкции, разреженное облако, 2.5D-сетка, отчёт | 3 × объём снимков |
| Сбалансированный | `--feature-quality high --pc-quality medium --dsm --orthophoto-resolution 5 --dem-resolution 10 --auto-boundary` | плотное облако, DSM, ортофотоплан, 3D-модель, отчёт | 8 × объём снимков |
| Высокое качество | `--feature-quality ultra --pc-quality high --dsm --dtm --orthophoto-resolution 2 --dem-resolution 5 --mesh-octree-depth 12 --auto-boundary` | то же + DTM, более детальная сетка | 15 × объём снимков |

Смысл параметров (из справки ODM 3.6.2): `--fast-orthophoto` — без плотной реконструкции и 3D-модели; `--feature-quality`/`--pc-quality` — качество признаков и плотного облака (каждый шаг `--pc-quality` примерно в 4 раза дольше); `--orthophoto-resolution`/`--dem-resolution` — см/пиксель, но не точнее оценки GSD; `--dsm`/`--dtm` — модели поверхности и рельефа; `--auto-boundary` — граница по точкам съёмки, отсекает фон; `--mesh-octree-depth` — детализация сетки.

Оценка места — грубый запас, а не обещание: реальный объём зависит от снимков и сцены.

### Дополнительные параметры

Поле «Дополнительные параметры ODM» принимает только параметры из списка (остальные отклоняются при проверке, до запуска):

`--dsm`, `--dtm`, `--fast-orthophoto`, `--skip-3dmodel`, `--skip-report`, `--auto-boundary`, `--use-3dmesh`, `--pc-ept`, `--feature-quality <ultra|high|medium|low|lowest>`, `--pc-quality <…>`, `--orthophoto-resolution <см>`, `--dem-resolution <см>`, `--min-num-features <N>`, `--mesh-octree-depth <1–14>`, `--max-concurrency <N>`.

Строка делится на аргументы как командная строка (кавычки группируют), но никогда не передаётся командной оболочке. Параметры, меняющие пути и контейнер (`--project-path`, флаги Docker и т. п.), недоступны.

## Результаты

| Вид | Файл в папке задания | Что проверяется и показывается |
| --- | --- | --- |
| Ортофотоплан | `odm_orthophoto/odm_orthophoto.tif` | заголовок (Big)TIFF и GeoKeys: EPSG, размер пикселя, размер, число каналов |
| DSM / DTM | `odm_dem/dsm.tif`, `odm_dem/dtm.tif` | то же |
| Облако точек | `odm_georeferencing/odm_georeferenced_model.laz` | сигнатура `LASF`, версия LAS, число точек из заголовка |
| 3D-модель | `odm_texturing/odm_textured_model_geo.obj` | наличие, размер |
| 2.5D-модель | `odm_texturing_25d/odm_textured_model_geo.obj` | наличие, размер |
| Отчёт | `odm_report/report.pdf` | сигнатура `%PDF` |

Пустые файлы не регистрируются. Для завершённого задания панель показывает, какие виды результатов не созданы в выбранном режиме. «Открыть» запускает программу, связанную с типом файла в системе (для GeoTIFF и LAZ — например, QGIS); «Открыть папку» открывает папку задания. Встроенный просмотр GeoTIFF и облаков — этапы C и D.

## Состояния задания

`queued` → `preparing` → `running` → `completed` / `failed` / `cancelled`; при отмене — промежуточное `cancelling`.

- **Отмена** в очереди — сразу; во время подготовки — после текущего файла; во время работы — `docker stop -t 10` (контейнер удаляется сам, `--rm`). Если клиент Docker не завершился за 10 с, контейнер удаляется `docker rm -f`.
- **Закрытие программы или проекта** во время обработки — только после подтверждения. Контейнер удаляется, задание получает состояние `interrupted`, файлы, уже созданные ODM, остаются.
- **Перезапуск после сбоя.** Задания, которые были активны, когда программа остановилась, после открытия проекта показываются как «Прервано» (никогда как завершённые); оставшийся контейнер `geomap-odm-<id>` удаляется.
- **Повторный запуск** создаёт новое задание в новой папке; результаты прежних заданий не трогаются.
- **Удаление задания** — только завершённого и только после подтверждения; удаляется папка `jobs/<id>/` целиком (жёсткие ссылки на снимки не затрагивают файлы в `photos/`). Удаление отказывается работать, если папка задания — ссылка или не находится прямо в `jobs/`.

## Файлы задания

```text
jobs/<id>/
  job.json     описание и состояние (schemaVersion 1), атомарная запись
  log.txt      заголовок GeoMap AI, команда docker, полный вывод ODM, итог
  images/      входные снимки (жёсткие ссылки или копии)
  …            рабочие папки и результаты ODM (opensfm/, odm_orthophoto/, odm_report/, …)
```

Формат `job.json` описан в `docs/PROJECT_FORMAT.md`.

## Диагностика

| Сообщение | Что сделать |
| --- | --- |
| «Docker не найден» | Установите Docker Desktop или задайте `GEOMAP_DOCKER`, затем «Проверить снова» |
| «Docker не запущен» | Запустите Docker Desktop, дождитесь готовности, «Проверить снова» |
| «Образ OpenDroneMap 3.6.2 не загружен» | «Загрузить образ ODM» (≈630 МБ) |
| Код 137 | Нехватка памяти Docker: профиль «Быстрый просмотр», меньше `--max-concurrency` или больше памяти в настройках Docker Desktop (WSL) |
| «завершился без ошибок, но результатов нет» | Смотрите `log.txt`: обычно мало перекрытия или нет совпадающих точек |
| «Не читаются снимки …» | Файл в `photos/` повреждён: удалите снимок из проекта или импортируйте заново |

Время и качество реконструкции не гарантируются: они зависят от перекрытия снимков, их качества, GPS/GCP и ресурсов компьютера.
